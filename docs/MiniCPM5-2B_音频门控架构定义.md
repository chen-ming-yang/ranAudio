## 1. 定位与设计目标

### 1.1 系统定位

一个**全双工语音交互系统**：快时钟 LM 槽位常驻，负责实时听、实时说、实时判断「要不要调工具」；需要真实执行能力时，把语义交给异步的慢时钟 LM 槽位完成。

链路与协议以 **§3.2** 为准。具体模型是可替换填充项（当前候选见 §3.2.4），未定时不得按 MiniCPM5-2B / Qwen3.5-27B 写死实现假设。

分工的**唯一原则**：

> **谁强谁承担推断责任。**
> FastLM 只做抽取式判断（这话要不要调工具、用户说了哪几个字），
> SlowLM 做推断式工作（消解、规划、参数生成）。

### 1.2 设计目标（按优先级）

| 优先级 | 目标 | 为什么是它 |
|---|---|---|
| P0 | **主循环永不阻塞** | 全双工的地基。任何一处 `await` 工具返回，双工即失效 |
| P0 | 交互延迟 ≤ 600ms 出声 | 超过此值用户感知为「卡顿」 |
| P1 | 路由准确率（尤其**召回**） | 漏判 = 2B 硬答实时问题 = 幻觉，是最高代价的失败 |
| P1 | 打断/重叠鲁棒性 | 决定体验是否「像人」 |
| P2 | 端侧算力/内存预算 | 决定能否落地手机/车机 |
| P2 | 27B 调用成本 | 可被 filler 与分级路由优化 |

### 1.3 非目标（明确不做）

- 2B 端语音 token 生成（外接 TTS，2B 输出文本即可）
- 2B 多步规划 / 多轮 slot filling（v0.1 只做**一轮** function call）
- 主动交互（主动提醒、环境播报）—— MiniCPM-o 4.5 的 1Hz 主动决策[citation:4] 属于后续版本
- 视觉模态

## 2. 核心决策：条件性 ASR

### 2.1 决策内容

**ASR 不是独立的前置模块，而是 2B 输出流中的一段。** 模型先吐路由 token，只有判为需要 function call 时才接着吐转写。

```
speak 路径：  <mode:speak><reply>今天天气不错，适合出门。</reply>
route 路径：  <mode:route><asr>帮我查一下北京天气</asr><filler>好的，我看看</filler>
```

正常回复路径**完全不产生转写文本**。

### 2.2 与其他方案的对比

| 方案 | 描述 | 优点 | 代价 |
|---|---|---|---|
| **A. 条件性 ASR（本方案）** | 转写是输出的一段，按需产出 | 省一段解码；端到端理解→回复，无文本中转 | 2B 端到端语音理解成为瓶颈；转写能力弱 |
| B. 总是 ASR（级联） | ASR→LLM→TTS | 转写质量稳定可控；模块可独立优化 | 每轮多一次完整转写；ASR 错误必然传播 |
| C. 双流语音原生（Moshi 式）[citation:19] | 用户流/助手流并行自回归 | 保留副语言信息；真正的语音到语音 | 需自研 speech tokenizer；2B 算力下质量存疑 |

### 2.3 决策依据与退路

选择 A 的理由：本系统的价值不在「转写得准」，而在「**实时判断要不要调工具**」。转写只是上派负载，不是产品形态。

**但这是可推翻的决策**，退路明确：

> **ASSUMPTION-A1**：2B 在简单闲聊/情感回应上的端到端语音理解准确率 ≥ 级联方案。
> 若 P0 实测不达标（2B 频繁听错导致答非所问），**退回方案 B**。
> 判定方式见 §9.1。

### 2.4 已知代价与缓解

- **转写能力偏弱**：`<asr>` 只在 route 样本上训练。**必做**——增设独立的 ASR 对齐阶段 S1.5（2B 完全冻结，大规模 ASR 只训 encoder + adapter），让转写能力沉淀在 encoder 侧。这同时也是解决「转写 × 生成」多任务冲突的主要手段，见 §10.3、§10.5。
- **实时字幕缺失**：若产品要求实时字幕，需额外跑轻量流式 ASR 旁路，恰好抵消省下的算力。规则见 §2.5。

### 2.5 字幕旁路规则（若启用）

> **硬规则：旁路 ASR 只用于 UI 展示，绝不参与上派。**
> 上派负载必须是主干产出的 `<asr>`。
> 两者不一致时**以主干为准**——主干是模型在理解上下文后生成的，通常比独立 ASR 更准。

## 3. 系统架构

### 3.1 分层

```
┌─────────────────────────────────────────────────────────────────────┐
│ L4  应用层      会话管理 · 工具沙箱 · 权限 · 审计                      │
├─────────────────────────────────────────────────────────────────────┤
│ L3  异步执行层   SlowLM Worker · 工具执行 · 结果回注                   │
│                 （慢时钟 0.5–5s，可取消，无状态于主循环）               │
├─────────────────────────────────────────────────────────────────────┤
│ L2  协调层      流解析 · 事件总线 · 状态机 · 播报仲裁                  │
├─────────────────────────────────────────────────────────────────────┤
│ L1  实时层      FastLM（门控+转写+回复）· Encoder 槽位                 │
│                 （快时钟 80–160ms，永不阻塞）                          │
├─────────────────────────────────────────────────────────────────────┤
│ L0  信号层      AEC · 麦克风 · TTS 播放与回采                          │
└─────────────────────────────────────────────────────────────────────┘
```

槽位含义与当前候选见 §3.2.4。

### 3.2 数据流

```
         ┌──────────────────────────────────────────────────┐
         │  快时钟 80–160 ms/chunk（永不阻塞）              │
         │                                                  │
         │  麦克风 ─► AEC ─► Encoder ─► Adapter ─► FastLM  │
         │            ▲                             │       │
         │            │  TTS 回采（回声参考）       │       │
         │                           单流自回归解码 │       │
         └──────────────────────────┬───────────────────────┘
                                    │
         ┌──────────────────────────▼───────────────────────┐
         │  首 token = 路由决策                             │
         │  <mode:speak | route>                            │
         └──────────────────────────┬───────────────────────┘
                                    │
      ┌─────────────────────────────┴──────────────────────┐
      ▼                                                    ▼
  <mode:speak>                                      <mode:route>
  <reply>正文                                       <asr>转写</asr>
      │                                                    │
      │                                        ① </asr> 闭合即上派
      │                                          （不等 filler 生成完）
      │                                                    │
      │                                        ② emit 事件（fire-and-forget）
      │                                                    ├───► <filler> ──┐
      │                                                    │                │
      │                                     ┌──────────────▼───────────┐    │
      │                                     │  SlowLM（慢时钟）        │    │
      │                                     │  一轮 FC：LLM(tools)     │    │
      │                                     │  → 执行 → 回填 → LLM     │    │
      │                                     │  → speak                 │    │
      │                                     └──────────────┬───────────┘    │
      │                                    ③ 结果事件回注   │               │
      │                                                    │                │
      └───────────────────┬────────────────────────────────┴────────────────┘
                          ▼
                ④ TTS 出口（两条路唯一汇合点）
                ┌──────────────────────┐
                │  分句 + 文本规整     │
                └──────────┬───────────┘
                           ▼
                     TTS 播放队列
                           │
                           └── 回采（回声参考）──► AEC
```

**四个关键分叉点**：
- **① 上派时机**：`</asr>` 闭合瞬间，不等 filler。这是延迟最优解。
- **② fire-and-forget**：主循环不等待。
- **③ 结果回注**：异步事件，播报时机由仲裁决定（见 §6.2）。
- **④ TTS 出口**：两条路的唯一汇合点，统一做分句与文本规整。

本节图是整体链路的**唯一脊柱**。后文协议（§4）、时钟（§5）、状态机（§6）都挂在这张图上，不另起并行数据流。

### 3.2.1 四条铁律

从图上四个分叉点落成约束。实现不得走样：

1. **`</asr>` 闭合即 emit**，不等 `<filler>` 生成完。
2. **emit 必须 fire-and-forget**：快时钟不得 `await` Worker，也不得等待工具返回。
3. **回注是事件，不是出声**：出声与否由播报仲裁决定（`no_op` / `speak=null` / 用户正在说则挂起，见 §6.2）。回注不得直达扬声器。
4. **两条路只有一个 TTS 汇合点**：speak 的 `<reply>`、route 的 `<filler>`、Worker 回注的 `speak` 只能进 ④；禁止旁路直接播。

### 3.2.2 模块与职责

按图上的框定义输入 / 输出 / 不得做什么。不规定实现语言或框架。

| 模块 | 层 | 输入 | 输出 | 不得做什么 |
|---|---|---|---|---|
| 麦克风 | L0 | 声学 | PCM chunk（80–160 ms） | — |
| AEC | L0 | 近端=麦；远端=TTS 回采 | 残差音频 | 不得把旁路 ASR 当残差源 |
| Encoder 槽位 | L1 | AEC 残差 chunk | 音频表示（流式） | 不得整段非流式堵住快时钟 |
| Adapter | L1 | 音频表示 | FastLM 隐空间 | — |
| FastLM 槽位 | L1 | Adapter 输出 | 单流自回归 token | 快时钟内不得等待网络 / 工具 |
| 首 token 路由 + 流解析 | L2 | token 流 | speak / route 分支 | 半标签处理必须满足 §4.2 |
| 事件总线 | L2 | dispatch / result / cancel | 单向投递 | 不得让快时钟 `await` |
| 播报仲裁 | L2 | 回注 + 交互状态（§6） | 是否允许 `tts.enqueue` | 回注不得直达扬声器 |
| SlowLM Worker | L3 | `route.dispatch` | `route.result` | 对主循环无状态；v0.1 只做一轮 FC |
| TTS 出口（④） | L2→L0 | `<reply>` / `<filler>` / 回注 `speak` | 分句 + 文本规整 | 禁止旁路绕过本口 |
| TTS 播放队列 | L0 | 规整后文本 | 播放音频 + 回采参考 | 回采只回 AEC，不回 FastLM 文本侧 |

SlowLM 一轮 FC 的顺序固定为：`LLM(tools) → 执行 → 回填 → LLM → speak`。

### 3.2.3 路径不变量

- **speak**：不产生 `<asr>`。正文只走 `<reply>`，流式进入 ④。
- **route**：`<asr>` 是上派的**唯一文本源**。`<filler>` 只进 TTS，不进 Worker。
- 上派负载沿用 §4.3（`request_id` / `asr_text` / `anchor_time` / `prev_utterance`）。本节不另发明第二套字段。
- 回注负载沿用 §4.4。`speak=null` 表示本轮不播报。

### 3.2.4 模型槽位

具体型号后续填充。每个槽位只规定**必须满足的能力**；当前候选仅作脚注，不是实现前提。

| 槽位 | 必须满足 | 当前候选 |
|---|---|---|
| **Encoder** | 流式、chunk-causal；输入 AEC 残差，输出音频表示 | **SenseVoice-Small**（[`ranAudio/sensevoice_apm.py`](../ranAudio/sensevoice_apm.py)；Whisper APM 仅保留给 v1.0 对照） |
| **FastLM** | 端侧可常驻；**首 token 即给出** `<mode:speak\|route>`；其后输出 §4.1 四段标签 | MiniCPM5-2B |
| **SlowLM** | 一轮 function call + 回填后再 `speak`；必须能按 `request_id` **取消**；必须能 `no_op`（`speak=null`） | Qwen3.5-27B |
| **TTS** | 文本进、音频出，并提供回采参考给 AEC | **OPEN**（未选型） |

槽位更换后：链路与协议不变；§10 训练规格须重做，不得把针对当前 FastLM 候选的阶段 / loss 当成与型号无关的硬约束。

### 3.2.5 事件与失败路径

总线只定义事件名与触发点。字段表见 §4.3 / §4.4，此处不重复。

| 事件 | 触发 | 去向 |
|---|---|---|
| `route.dispatch` | `</asr>` 闭合（铁律 1） | SlowLM Worker |
| `route.result` | Worker 完成 / 失败 / 取消 | 播报仲裁，不得直达扬声器 |
| `route.cancel` | 打断确认 | Worker；FastLM 侧回滚见 §6.3 |
| `tts.enqueue` | 仲裁放行后的唯一入口 | TTS 播放队列 |

失败影响与 §5 一致：

- **慢时钟**超时 / `error`：降级为本地应答，或闭嘴（`speak=null`）。交互不中断。
- **快时钟**失败：交互中断。这是唯一允许打断主循环的失败。
- 取消语义与回滚深度见 §6.3，本节不展开状态机。

## 4. 输出协议

### 4.1 Token 流格式

所有信息在**单一自回归序列**中，无并行流。

| 段 | 标签 | 出现条件 | 消费方式 |
|---|---|---|---|
| 路由 | `<mode:speak>` / `<mode:route>` | 必选，首段 | L2 状态机 |
| 转写 | `<asr>…</asr>` | 仅 route | 闭合即上派 |
| 垫话 | `<filler>…</filler>` | 仅 route | 立即送 TTS |
| 回复 | `<reply>…</reply>` | 仅 speak | 流式送 TTS |

**v0.1 只定义此四段。** 预留扩展：`<state>`（交互状态）、`<barge>`（打断标记）。

### 4.2 流式解析约束（实现必须满足）

标签会被切在不同 token 中（`<as` + `r>帮我查`）。解析器必须满足：

1. **半个标签保留**：pending 是标签前缀时**原样保留**等补齐，不得清空（清空会导致后续 token 无从拼接，标签残骸漏进正文）。
2. **前缀显式等待**：三态判定——完整匹配→剥离 / 是前缀→等待 / 都不是→降级。缺失「等待」态会导致半个标签被判为正文。
3. **降级不等长度**：一旦确定不是任何标签前缀，立即降级为 speak 正文。不得等攒够固定长度（中文短句永远凑不齐，会导致整句不播报）。
4. **异常不吞**：`</asr>` 未闭合时，有多少用多少照常上派。

> 实现备注：这四条是此类设计的通用陷阱，与具体语言无关。验收需覆盖 1/2/3/5/7/N 多种切分粒度 + 无标签降级 + 标签未闭合。

### 4.3 上派负载

```jsonc
{
  "request_id":  "req_xxx",        // 用于取消
  "asr_text":    "帮我查一下北京天气",  // 主干产出，非旁路 ASR
  "anchor_time": "2026-09-10T14:23:00+08:00",  // 用户说话时刻，解析「明天」必需
  "prev_utterance": "…"            // 上一句用户原话（仅 route 时有）
}
```

**`anchor_time` 必带**。缺了它，27B 无法解析任何相对时间表达。用**说话时刻**，不是接收时刻。

### 4.4 回注负载

```jsonc
{
  "request_id": "req_xxx",
  "status": "ok | need_clarify | no_op | cancelled | error",
  "speak": "北京明天多云转晴，18到24度。",   // null = 本轮不播报
  "tool_trace": [...]
}
```

`no_op` 是**必要的**：worker 默默更新了信息但无需打扰用户时，必须能闭嘴。全双工里「没事找事式插播」是高频体验杀手。

## 5. 时钟模型

| | 快时钟 | 慢时钟 |
|---|---|---|
| 周期 | 80–160 ms/chunk | 0.5–5 s |
| 承载 | 听、说、路由决策 | function call 执行 |
| 阻塞 | **永不** | 可被取消 |
| 失败影响 | 交互中断 | 降级为本地应答 |

**铁律**：快时钟内不出现任何网络/工具等待。所有跨时钟交互通过事件总线，单向 fire-and-forget + 异步回注。

## 6. 状态机

### 6.1 交互状态

五状态，覆盖全双工主要情形：

| 状态 | 含义 | 进入 | 退出 |
|---|---|---|---|
| `LISTEN` | 听，未决策 | 静默/开启 | 端点检测触发 |
| `SPEAK` | 播报中 | 决策为 speak / 收到回注 | 播完或被打断 |
| `ROUTE_WAIT` | 已上派，等结果 | `</asr>` 闭合 | 结果回注 / 取消 |
| `DUAL` | 重叠（双方同时说） | 播报中检测到用户语音 | 判定为 backchannel 或 barge-in |
| `BARGE_IN` | 被打断 | 确认打断 | 取消在途，转 LISTEN |

> `WAIT`（静默但未结束）与 `DUAL` 是区别于简单 speak/listen 二分的关键：
> 停顿不等于说完，重叠不等于打断。

### 6.2 播报仲裁（关键规则）

> **用户正在说话时，不主动插入播报。**
> 回注结果到达时若处于 `LISTEN`/`DUAL`（用户在说），挂起到 `on_silence` 再播。

违反此规则的典型失败：用户正说着，AI 硬插一句上一轮查的天气。

### 6.3 取消语义

- `barge_in` → 对 `request_id` 发 `cancel`
- 2B 侧状态回滚到上派前快照
- **worker 侧回滚深度由 worker 决定**（v0.1 单轮 FC，通常整体丢弃）

**OPEN-1**：多轮任务下 worker 回滚深度（整体丢弃 / 保留已完成副作用）未定义。副作用不可逆时（如已下单）的补偿语义需单独设计。

### 6.4 回声与打断

- **信号层**：WebRTC AEC，TTS 播放音频作为参考
- **模型层**：训练时混入 TTS 播放音频 + 用户插入音频的随机偏移，标注忽略/打断
- 打断检测建议采用 **chunk 级状态预测**（模型最后一层挂分类头），而非外挂 VAD

**OPEN-2**：CF（通道融合）与 XA（cross-attention 路由）的选择。研究显示 CF 语义更强但打断时易产生错乱续生成，XA 打断鲁棒性更好[citation:26]。**当前倾向混合**——主干 XA 保播放连贯，门控分支 CF 保语义。

## 7. 端到端时序

### 7.1 正常回复（speak）

```
t=0     端点检测
t=50    <mode:speak> 吐出        → 路由确定
t=80    首个分句送 TTS
t=350   首包出声                 ← 用户感知延迟
t=1.2s  全部播完
```

### 7.2 Function call（route）

```
t=0     端点检测
t=50    <mode:route>
t=200   </asr> 闭合              → 立即上派 ①
t=230   <filler> 出声            ← 用户感知延迟 ≈ 400ms
t=230+  27B 执行（1–3s）
t=2.5s  结果回注 → 播报
```

**filler 的作用**：把用户感知延迟从「工具往返 1–3s」压到「首包 400ms」。这不是锦上添花，是这条路能否可用的关键。

### 7.3 打断

```
t=0     上派 req_a
t=200   用户插话（VAD/chunk 预测）
t=200   cancel(req_a)，2B 状态回滚
t=250   处理新输入
```

### 7.4 延后播报

```
t=0     上派 req_a
t=1.5s  req_a 结果回来，但用户在说话 → 挂起
t=3.0s  on_silence → 播报
```

## 8. 延迟预算

| 环节 | 预算 | 备注 |
|---|---|---|
| 音频 chunk | 80–160 ms | 下采样至 ~12.5Hz 与文本 token 率接近 |
| 端点检测 | 100–300 ms | 语义端点优于纯静音检测 |
| 路由决策 | 1 个 token | 本设计的核心优势 |
| 首包出声（speak） | 300–600 ms | 含 TTS 首包 |
| 首包出声（route，靠 filler） | 350–500 ms | |
| 结果播报（route） | +1–3 s | 被 filler 掩盖 |

**ASSUMPTION-A2**：2B 在目标硬件（INT4，端侧 NPU/CPU）上解码速率 ≥ 20 tok/s。低于此值 filler 策略失效，需重新评估。

## 9. 验证与评测

### 9.1 推翻 ASSUMPTION-A1 的判定实验（P0）

构造对照集（各 200 条，覆盖：问候、闲聊、情感回应、简单知识、指令），对比：

- **准确率**：语义是否正确
- **听错率**：是否因误识别而答非所问

**判定**：若 2B 端到端方案在「听错率」上显著劣于级联（> 1.5×），退回方案 B。

### 9.2 路由指标（P1）

| 指标 | 定义 | 目标 |
|---|---|---|
| **召回** | 该上派且上派 / 该上派 | **≥ 0.95**（优先保证） |
| 精确 | 该上派 / 实际上派 | ≥ 0.80 |
| 转写 CER（route 子集） | 字符错误率 | ≤ 0.08 |
| **实体 / 数字保真率**（route 子集） | 专名、数字、时间未被「脑补」改写的比例 | ≥ 0.98 |

**召回优先于精确**：漏判代价（幻觉）远高于误判代价（多花一次延迟）。工作点应偏向「宁可多上派」。

> **CER 看不出「脑补」**：把听到的词改写成另一个合理词，CER 可能仍达标，但上派负载已被污染。因此必须同时测实体/数字保真率（详见 §10.5）。

### 9.3 交互指标（P1）

打断成功率、误打断率（backchannel 误判为打断）、重叠播报率、首包延迟 P50/P95。

## 10. 训练规格

> 本节针对**当前快时钟 LM 候选**（MiniCPM5-2B）及配套 encoder。槽位更换后须重做阶段划分与 loss，不得把本节当作与型号无关的硬约束。

### 10.1 数据格式

```
speak 样本：  <audio> → <mode:speak><reply>…</reply>
route 样本：  <audio> → <mode:route><asr>…</asr><filler>…</filler>
```

> **数据量级**：S1.5 阶段的 ASR 用量应**显著大于** S2 中的 ASR 部分——转写能力主要靠 S1.5 沉淀在 encoder，S2 只需让主干学会「按指令吐转写」（§10.3、§10.5）。

### 10.2 Loss 策略

| 段 | 权重 | 理由 |
|---|---|---|
| `<mode:speak\|route>` | **≥ 1.0**（单独提权） | P1 核心指标，不得被其他段稀释 |
| `<reply>` / `<filler>` | 1.0 | 这是 2B 的核心产出 |
| `<asr>` | **0.1–0.3**（降权，非 mask） | 转写质量主要由 encoder 决定（§10.5）；主干只需学会「按指令吐转写」，不是当 ASR 用 |

- **纯文本回放用「交错」而非「混批」**：dataset-level 简单混合无法把文本侧能力迁移到语音侧（模态鸿沟）——文本侧指标大涨而语音侧几乎不动。应在对齐的语音-文本对内部构造 **segment 级交错序列**（按静音 + 标点切分），让同一 decoder 在语音段与文本段之后都预测文本，显式保住生成先验。
- **先分后混**：三任务先各自收敛再混合，或交替 batch，不要一开始就随机混合。

> 完整的冲突分析与缓解方案见 §10.5。

### 10.3 阶段划分

| 阶段 | 目标 | 冻结 |
|---|---|---|
| S0 模态对齐 | encoder + adapter | 冻结 2B |
| S1 流式化 | encoder 改 chunk-causal | 冻结 2B |
| **S1.5 ASR 对齐（关键）** | 大规模 ASR 训练，让转写能力沉淀在 encoder | **2B 完全冻结（不开 LoRA）**；encoder 用预训练 ASR 模型初始化 |
| S2 三任务 SFT | 对话 / 路由 + **少量**转写 | **2B 用 LoRA，不全参** |
| S3 路由校准 | 扫 operating point | 免重训调阈值 |
| S4 双工专项 | 合成重叠语音，训打断与回声忽略 | LoRA |

**硬约束**：2B 不得全参微调。语音化后文本智能退化是这类系统的典型失败模式。

> **S1.5 是全表最关键的一行**：它把绝大多数转写监督关进一个「2B 不可写」的时间窗，是 §10.5 多任务冲突的主要解法。
> 参照 Phi-4-Multimodal（3.8B 底座，OpenASR 榜首 + 语音对话/摘要能力兼得）：对齐阶段用约 2M 小时 ASR 且**解码器冻结、只训 encoder + projector**；之后的多任务 SFT 中 ASR 仅占约 28%。对齐阶段结束时模型「只能做 ASR」，指令跟随能力是后一阶段才解锁的。

### 10.4 负例构造（关键）

> **必须让 2B 自己先答一遍，能答对的标 speak。**

否则模型会发现「上派总是安全的」，退化为全部上派，路由机制失效。Hard negative 重点覆盖：闲聊、角色扮演、简单算术、2B 能力内的知识问答。

**OPEN-3**：负例与正例的比例、以及「2B 自答判定」的自动化流程未定义。

### 10.5 多任务冲突：转写 × 生成（关键）

**问题**：`<asr>` 是高保真复述（需**压制**语言先验），`<reply>` 是自由生成（需**依赖**语言先验）。两者共享同一个 decoder，争夺输出倾向。

冲突是**非对称**的——ASR 对生成能力的伤害远大于反向。

**实证参照**：Speech-LLM 在 ASR 监督主导时，decoder 会向语音条件建模过度特化，削弱文本预训练获得的生成先验。7B 底座（5T token 预训练）在 ASR-only 适配后，zero-shot 语音问答退化到接近 0；且**单纯混入纯文本数据无法把文本侧能力迁移到语音侧**——文本侧指标大涨而语音侧几乎不动，即模态鸿沟。有效手段是让同一 decoder 在语音段与文本段之后都做同形式的 next-token 预测。

**2B 放大风险**：容量越小，任务挤占越明显。7B 尚且被主导，2B 更容易被转写任务吃掉生成先验。

#### 决策：阶段隔离（在 2B 冻结期把 ASR 训够）

> **主决策：把绝大多数转写监督放进一个「2B 完全不可写」的独立阶段（S1.5）；主干在 S2 只保留轻权重的 `<asr>` 监督。**

**原理**：转写与生成的冲突，本质是它们在同一批**可写参数**上竞争。把 ASR 监督关进一个主干被冻结的时间窗，转写在物理上够不到生成先验——这比在架构上加辅助 head 更简单，且已在 2M 小时规模上验证过。

参照 Phi-4-Multimodal（3.8B 底座 + 语音 LoRA，OpenASR 榜首同时保留对话能力）的两阶段范式，落到本项目：

1. **S1.5 ASR 对齐阶段**（必做，见 §10.3）：2B **完全冻结（连 LoRA 都不开）**，只训 encoder + adapter，用**大规模** ASR 数据。encoder 用预训练 ASR 模型初始化，不从零对齐。阶段结束时模型「只会转写」，这是预期状态，不是缺陷。
2. **S2 大幅缩减 ASR 数据**：主干只需学会「按 `<mode:route>` 指令吐出转写」，不需要靠它学发音对齐——后者已由 S1.5 的 encoder 承载。
3. **主干 `<asr>` 轻权重**：0.1–0.3（§10.2）。
4. **路由 token 提权**：`<mode:speak|route>` ≥ 1.0，不被转写稀释。
5. **文本回放改交错 + 先分后混**（§10.2）。
6. **可选增强：encoder 侧辅助 ASR head**（OPEN-7）——不占主干容量，但**不是主路径**；阶段隔离已能覆盖大部分收益。

**正面效应**：ASR 监督对 encoder 的对齐与 grounding 有真实收益，能减少「听错导致的答非所问」。要隔离的是**占用主干生成容量**的那部分，不是 ASR 本身。

#### 三个必须监控的失效信号

| 信号 | 表现 | 危险点 |
|---|---|---|
| **转写脑补** | `<asr>` 出现用户没说的词；实体、数字被「纠正」 | 污染上派负载；§2.5 禁止旁路 ASR 纠正，错误直传 27B |
| **回复复读化** | `<reply>` 复述用户的话而不回答 | 直接触发 §2.3 的 ASSUMPTION-A1 退路判定 |
| **上派率漂移** | 上派率随训练单调上升 | 转写比生成「更容易降 loss」，是 §10.4「全部上派」的第二条成因 |

**CER 看不出脑补**：把听到的词改写成另一个合理词，CER 可能仍达标而语义已被污染。必须同时测**实体/数字保真率**（§9.2）。

#### 判定实验（S2 前必做）

扫 `<asr>` loss 权重 `{0, 0.1, 0.3, 1.0}`，同时记录三条曲线：

1. 上派率
2. route 子集 CER **+ 实体/数字保真率**
3. speak 路径复读率

取拐点作为工作点。另用**纯文本问答 T2T vs S2T 的差值**诊断生成先验保留度：Δ 越接近 0 越好。

**OPEN-7**：encoder 侧辅助 ASR head（可选增强）的形态（CTC / 轻量 decoder）与挂载位置（encoder 输出 / adapter 输出）未定；S1.5 的 ASR 数据规模与 S2 中 ASR 占比的最优配比也需实测。

| ID | 问题 | 影响 | 收敛时点 |
|---|---|---|---|
| **OPEN-1** | 多轮任务下 worker 回滚深度与副作用补偿 | 高（涉及资金/订单安全） | v0.2 前 |

| **OPEN-3** | 负例构造比例与自动化流程 | 中（决定路由是否退化） | S2 前 |
| **OPEN-4** | 任务级迟滞是否纳入 v0.1 | 中（决定多轮省略句能力） | v0.2 决策 |
| **OPEN-5** | 27B 分级（新任务 pro / 续接 lite）必要性 | 中（成本） | 成本实测后 |
| **OPEN-6** | 端点检测：语义端点 vs 静音端点 | 中（延迟） | P0 |
| **OPEN-7** | 辅助 ASR head 形态（CTC / 轻量 decoder）与挂载位置 | 中（决定转写监督能否外置） | P0 实测 |

### 关于 OPEN-4 的说明（v0.1 明确不做）

v0.1 的路由是**无状态二分类**。这意味着「那明天呢」「要靠窗的」这类**省略句无法被正确路由**——2B 单独看这句提取不出任何意图信号。

已知解法是**任务级迟滞**：任务进行中默认上派，只判是否离题/终止。但这需要 `task_id` 粘性与任务状态，显著增加复杂度。

**v0.1 的取舍**：先接受这个缺陷，用一轮 FC 的简化换架构可验证性。**v0.2 必须解决**，否则多轮对话不可用。

## 12. 风险登记

| 风险 | 影响 | 缓解 |
|---|---|---|
| 2B 端到端理解不达标 | 架构基础动摇 | 退回方案 B（§2.3） |
